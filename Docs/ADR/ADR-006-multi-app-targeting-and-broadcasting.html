Multi-App Token Isolation & Selective Broadcasting in FCM

Complete architectural guide on how Firebase isolates multiple apps (App A vs App B) inside a single project, how tokens work per user/app, and how to broadcast to one app without touching the other.

The Fundamental Question

"If I have App A (Customer) and App B (Driver) under the same Firebase project, how does Firebase know which app to ring? If I want to broadcast to ONLY App A, how is that guaranteed?"
This document explains the cryptographic token binding, backend registry routing, and Pub/Sub topic architecture that makes this 100% leak-proof.

1. The Firebase Hierarchy: Project vs. Apps

A Firebase Project is a parent container. Inside that single project, Google allows you to register up to 30 distinct mobile and web applications.

The Service Account key (service-account.json) lives at the Project level, giving your .NET backend administrative authority over all apps in that project.

Figure 6.1: One Firebase Project containing multiple independent applications

2. The Token Formula: Why Tokens Never Leak Across Apps

A common misconception is that a user only has one token or that an app shares tokens across users. In reality, FCM tokens are mathematically bound to three variables:

FCM Device Token = [ Specific Physical Device ] + [ App Bundle / Package ID ] + [ Firebase Project ID ]
Figure 6.2: Tokens are physically isolated per app, even on the exact same smartphone

3. Unicasting to a Specific App Only

When Alex uses both the Customer App and the Driver App, our gateway allows business microservices to target only one app using the appId field:

POST /api/notifications/send — Push to App A OnlyJSON
{
  "userId": "alex@company.com",
  "appId": "CustomerApp",
  "title": "Your Order is on the way! 🍕",
  "body": "Courier is 5 minutes away."
}

How the Backend Router Executes This:

  1. Queries Redis/Postgres device registry for user alex@company.com.
  2. Retrieves all registered tokens: Token_Alex_AppA (appId: CustomerApp) and Token_Alex_AppB (appId: DriverApp).
  3. Filters by d.AppId == "CustomerApp", discarding the driver token.
  4. Dispatches exclusively to Token_Alex_AppA.
  5. Result: Alex's Customer App displays the order banner. Alex's Driver App receives zero notifications.

4. Broadcasting to All Users of App A (And ZERO Users of App B)

When marketing or product teams want to send a global announcement to all 500,000 users of App A, how do you prevent App B users from receiving it?

Figure 6.3: Topic Pub/Sub fan-out to millions of App A devices with zero impact on App B

The 3 Approaches to Broadcasting to App A:

Method How it works Speed When to use
Method 1: FCM Topics (Pub/Sub) ⭐ App A auto-subscribes to appA_all on startup. Backend pushes to that topic with 1 single HTTP call. Instant (<3s) across millions of devices. Standard / Recommended for production. Zero server RAM or database load.
Method 2: Backend DB Multicast Backend queries database: SELECT token FROM devices WHERE appId = 'AppA' and sends batches of 500. Moderate (takes ~1-2 mins to loop through 500k tokens in batches). When you need to personalize each broadcast (e.g. inject user's first name into body).
Method 3: Firebase Console UI Marketer opens Firebase Console web dashboard, clicks "New Campaign", and selects target app dropdown. Instant Google scheduling. Non-technical marketing campaigns without writing code.

5. Client Implementation: Auto-Subscribing to App Topics

To implement Method 1, add this one-line subscription when App A initializes:

Swift (iOS):

AppDelegate.swiftSwift
// Inside App A only:
Messaging.messaging().subscribe(toTopic: "appA_broadcast") { error in
    if error == nil {
        print("✅ App A subscribed to global broadcast topic.")
    }
}

Kotlin (Android):

MainActivity.ktKotlin
// Inside App A only:
FirebaseMessaging.getInstance().subscribeToTopic("appA_broadcast")
    .addOnCompleteListener { task ->
        if (task.isSuccessful) {
            Log.d("FCM", "✅ App A subscribed to global broadcast topic.")
        }
    }

Triggering the Broadcast from Backend:

POST /api/notifications/sendJSON
{
  "topic": "appA_broadcast",
  "title": "Weekend Flash Sale! 🎁",
  "body": "50% off all items exclusively in App A.",
  "priority": "High"
}

6. Architectural Summary & Guarantees

Key Guarantees
  • Guaranteed Isolation: Because device tokens are cryptographically generated using each app's unique Bundle ID (com.company.customer vs com.company.driver), it is physically impossible for an App A token to wake up App B on any device.
  • Single Project Simplicity: You do NOT need separate Firebase projects to achieve total separation. 1 Firebase project + distinct Bundle IDs + Topic names gives you 100% isolation with zero extra infrastructure costs.
  • Effortless Scale: Topic broadcasts allow you to reach 10 million App A devices with 1 single HTTP call to our gateway.
