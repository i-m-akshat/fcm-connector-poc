ADR-005 Approved

Unified Multi-Type Notification Payload Contract

Eliminating fragmented push endpoints in favor of a single composable contract supporting Alert, Silent, Rich Media, Actionable, Collapsible, and Topic delivery.

1. Context & Problem Statement

Many push notification gateways split delivery logic across several disparate endpoints (e.g. /api/push/alert, /api/push/silent, /api/push/topic). This approach introduces several major architectural drawbacks:

  • API Fragmentation: Upstream developers must maintain separate client bindings and choose between rigid, siloed endpoints.
  • Lack of Composability: Real-world scenarios often require combining multiple features (e.g. an Alert notification that also has an Image, custom Data dictionary, and a Collapse Key to prevent tray clutter). Fragmented endpoints cannot handle this without creating combinatoric endpoint explosions.
  • Code Duplication: Validation, presence checking, and token registry lookups get duplicated across controller actions.

2. Decision Drivers

  • Single unified entry point for all internal backend services: POST /api/notifications/send.
  • Full composability of delivery attributes (Silent, Rich Image, Action Category, Live ETA collapse key, Priority).
  • Polymorphic target resolution (supports UserId, DeviceToken, Topic, or Condition in the same request model).
  • Automatic platform compilation: The gateway compiles the single request into Apple APNs HTTP/2 headers and Android Channels automatically.

3. Decision Outcome

Approved Decision: Establish NotificationRequest as the single canonical API contract for all push delivery. The NotificationDeliveryRouter compiles properties into platform-specific native structures at runtime:

Models/Contracts.cs — Unified ContractC#
public class NotificationRequest
{
    // Targets (at least one required)
    public string? UserId { get; set; }
    public string? DeviceToken { get; set; }
    public string? Topic { get; set; }
    public string? Condition { get; set; }

    // Multi-tenant override (optional)
    public string? AppId { get; set; }

    // Content
    public string? Title { get; set; }
    public string? Body { get; set; }
    public string? ImageUrl { get; set; }
    public Dictionary<string, string>? Data { get; set; }

    // Delivery Behaviors
    public bool IsSilent { get; set; }
    public bool OnlyIfActive { get; set; }
    public string? CollapseKey { get; set; }
    public string? ActionCategory { get; set; }
    public NotificationPriority Priority { get; set; } = NotificationPriority.Normal;
}

4. Platform Header Compilation Logic

Contract Field Android FCM Output Apple APNs Output
IsSilent = true Omits Notification block; delivers pure data map. Sets apns-push-type: background and content-available: 1.
ImageUrl = "https://..." Embeds Image in AndroidNotification (BigPicture). Sets fcm_options.image for APNs rich attachment.
CollapseKey = "ETA_102" Sets CollapseKey = "ETA_102". Sets apns-collapse-id: "ETA_102" in APNs headers.
Priority = Critical Sets Priority = High, channel critical_channel. Sets apns-priority: 10, interruption-level: time-sensitive.
ActionCategory = "RIDE" Sets ClickAction = "RIDE". Sets category: "RIDE" in APNs payload.

5. Consequences

Positive Impact
  • Developer Simplicity: Upstream microservices only ever need to integrate with 1 HTTP endpoint.
  • Maximum Flexibility: Any combination of notification features can be enabled simultaneously.
  • Client Agnostic: The caller does not need to know whether the user has an iPhone, an Android phone, or both.
