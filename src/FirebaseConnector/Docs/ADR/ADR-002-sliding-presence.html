ADR-002 Approved

Active Presence Tracking via Redis Sliding TTL

Decentralized 45s heartbeat and 90s sliding expiration mechanism to prevent notification noise on idle or offline devices.

1. Context & Problem Statement

In high-frequency operational domains (e.g. real-time ride dispatching, active order tracking, live vehicle radar), upstream microservices generate thousands of updates per minute. Pushing every update unconditionally to all registered tokens leads to serious operational issues:

  • Notification Spam: When users lock their phone or place the app in background, queuing 50 notifications creates lock screen clutter.
  • Battery & Resource Drain: Waking up devices for stale updates exhausts client batteries and cellular data plans.
  • Wasted Gateway Egress: Upstream services waste cloud egress and FCM rate limits sending messages to users who have gone offline.

2. Decision Drivers

  • Sub-millisecond presence lookup latency during notification dispatch.
  • Automatic expiration without requiring manual logout requests (handling app crashes, dead battery, or lost connectivity).
  • Stateless scale-out: Any backend instance behind a load balancer must be able to check user presence uniformly.

3. Considered Architecture Options

Architecture Option Pros Cons
Option 1: PostgreSQL / Relational DB Timestamp Reuses existing database. High disk I/O under frequent 45s heartbeats; requires continuous vacuuming of dead tuples.
Option 2: In-Memory MemoryCache (Single Process) Extremely fast, zero dependencies. Fails in multi-replica deployments; presence state is lost on pod restart.
Option 3: Redis Key Expiration (Sliding TTL) (Selected) In-memory speed (<1ms), native atomic TTL expiration, shared across all API replicas. Introduces dependency on Redis cluster.

4. Decision Outcome

Chosen Option: Option 3. Implement active presence tracking in Redis using a 45-second client heartbeat cadence and a 90-second sliding expiration window.

  • When an app registers or starts, it sends an initial heartbeat: POST /api/presence/heartbeat.
  • Every 45 seconds while foregrounded, the client repeats the ping.
  • Redis stores the key presence:{userId} with EXPIRE 90 seconds.
  • If 90 seconds pass without a heartbeat, Redis automatically evaporates the key.
  • When a push request specifies "onlyIfActive": true, the router checks await presenceService.IsUserActiveAsync(userId). If inactive, the push is discarded without calling Google FCM.

5. Implementation Blueprint

Services/PresenceService.csC#
public async Task RecordHeartbeatAsync(string userId, string deviceId)
{
    var db = _redis.GetDatabase();
    var key = $"presence:{userId}";
    // Store device metadata and set sliding 90s window
    await db.StringSetAsync(key, deviceId, TimeSpan.FromSeconds(90));
}

public async Task<bool> IsUserActiveAsync(string userId)
{
    var db = _redis.GetDatabase();
    return await db.KeyExistsAsync($"presence:{userId}");
}

6. Consequences & Metrics

Positive Impact
  • 70%+ Reduction in Non-Urgent Push Traffic: Dispatches to dormant or backgrounded devices are eliminated.
  • Zero Zombie State: Devices that crash or lose signal automatically become inactive after 90 seconds.
  • Instant Presence Recovery: As soon as a user unlocks and opens the app, the first heartbeat renews active status immediately.
