💓 Presence & Sliding TTL Lifecycle

How real-time heartbeats and Redis sliding expiration eliminate phantom notifications to inactive devices.

1. The Problem: Phantom Notifications

In high-throughput logistics, ride-hailing, and dispatch applications:

  • Drivers lock their screens, step away from vehicles, or lose cellular connectivity.
  • If the backend sends high-frequency ride offers to an offline driver, the customer waits for an offer that will never be accepted.
  • Battery life on mobile phones degrades rapidly from unnecessary radio wakeups.

2. The Solution: 45s Heartbeat & 90s Sliding TTL

The 2:1 Safety Ratio

Mobile clients ping every 45 seconds while the app is in the foreground. Each ping resets the Redis expiration to 90 seconds. This gives mobile devices a 2x safety window to survive minor cellular network dropouts without being marked offline prematurely.

3. Presence API Endpoints

1. Send Heartbeat (Extends Sliding Window)

POST /api/presence/heartbeat
{
  "userId": "driver_alex@company.com",
  "deviceId": "eF91k...raw_device_token..."
}

// Response:
{
  "status": "PresenceExtended",
  "ttlSeconds": 90
}

2. Mark Inactive (App Minimized / Backgrounded)

POST /api/presence/inactive
{
  "userId": "driver_alex@company.com",
  "deviceId": "eF91k...raw_device_token..."
}

3. Check User Presence Status

GET /api/presence/driver_alex@company.com

// Response:
{
  "userId": "driver_alex@company.com",
  "isActive": true,
  "activeDevices": [ "eF91k..." ]
}

4. How the Dispatch Router Uses Presence

When sending a notification via POST /api/notifications/send:

  • If "onlyIfActive": true is set, the router checks Redis. If the user has no active devices with valid TTL, dispatch terminates immediately with: 
    {
  "success": false,
  "reason": "UserInactive",
  "deliveredCount": 0
}
  • If "onlyIfActive": false is set, presence check is bypassed and the message is delivered to all registered devices regardless of presence state.
